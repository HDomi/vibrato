# 에이전트 역할 분담 고도화 계획

작성: 2026-11-24 · 상태: 계획 (미착수)

코드를 고쳐야 하는 요청을 역할별로 나눠 처리하고, 계획 탭에서 역할 · 주고받기 · 계획 변경 · 예외 상황까지 한눈에 보이게 한다.
일반 질문, 바로 답할 수 있는 요청은 지금처럼 메인 세션이 혼자 답한다.

## 1. 확정한 결정

| # | 결정 | 이유 |
|---|------|------|
| D1 | A(총괄)와 D(코더)는 **메인 세션 하나**가 겸한다 | 코더가 대화 맥락을 가장 많이 필요로 한다. 넘기는 지점이 없으면 세부 손실이 없다 |

## 2. 역할 구성

| 역할 | 실행 주체 | 하는 일 | 도구 | 모델 |
|------|----------|---------|------|------|
| A 총괄 | 메인 세션 | 요청 판별, 역할 배정, 자료 확인 · 사용자 질문, 결과 반영 | 전부 | 세션 모델 |
| B 기획 | 하위 `vibrato-planner` | 기획 문서를 읽고 요구사항 · 빠진 항목 반환 | 읽기 전용 (`disallowedTools`: Edit, Write, NotebookEdit, Bash) + 사용자 MCP(Notion 등) | sonnet / medium |
| C 디자인 | 하위 `vibrato-designer` | 시안 · 캡처를 읽고 배치 · 문구 · 수치 반환 | B 와 동일 + Figma MCP | sonnet / medium |
| D 코더 | 메인 세션 | 수정 · 생성 | 전부 | 세션 모델 |
| E 검증 | 하위 `vibrato-verifier` | 브라우저 실측, 테스트 · 프로세스 실행, 통과/실패 반환 | Bash, Vibrato 브라우저 MCP, 읽기 (`disallowedTools`: Edit, Write, NotebookEdit) | sonnet / medium |

- 도구는 우선 `disallowedTools` 로 막는다. 사용자가 붙인 MCP(Notion, Figma) 이름을 미리 알 수 없기 때문이다.
  P4 에서 세션 init 의 도구 목록으로 역할별 허용 목록(B 는 Notion 류, C 는 Figma 류, E 는 vibrato)을 만들 수 있는지 확인하고, 되면 `tools` 허용 목록으로 바꾼다(§3.9 T2).
- 하위 에이전트의 Bash · MCP 승인은 메인과 같은 `canUseTool` 을 거친다. 권한 모드가 그대로 적용된다.
- 이름에 `vibrato-` 접두사를 붙여 사용자 자신의 에이전트 정의와 겹치지 않게 한다.

## 3. 핵심 설계

### 3.1 구조화 계획 도구 `plan_set`

`server/browserMcp.ts` 의 `PLAN_TOOLS` 에 추가한다. Claude · Codex 둘 다 같은 MCP 로 받는다.

```jsonc
plan_set({
  "steps": [
    { "id": "s1", "role": "B", "title": "결제 기획서 요구사항 확인" },
    { "id": "s2", "role": "C", "title": "결제 화면 시안 수치 확인" },
    { "id": "s3", "role": "D", "title": "결제 버튼 영역 수정" },
    { "id": "s4", "role": "E", "title": "결제 화면 브라우저 실측" }
  ],
  "reason": "첫 계획"            // 두 번째 호출부터 필수: 왜 바꾸는지
})
plan_step({ "id": "s3", "note": "버튼 간격 12px → 16px, 문구 i18n 키 추가" })   // step 번호도 계속 받는다
```

서버 검증 규칙 (어기면 `isError` 로 이유를 돌려주고, 모델이 고쳐서 다시 부른다):

1. `id` 는 `s` + 숫자, 계획 안에서 유일하다. 지워진 id 를 다시 쓰지 못한다.
2. `role` 은 `A` `B` `C` `D` `E` 중 하나다.
3. 단계 수는 1~12 개다.
4. 이미 완료된 단계는 빼지 못한다. 빠지면 "s2 는 완료됐으니 남겨 두라"고 돌려준다.
5. 두 번째 호출부터 `reason` 이 없으면 거절한다.

글 계획("진행 계획" + 번호 목록)은 사람이 읽는 용도로 계속 쓴다. `plan_set` 을 부른 턴에서는 체크리스트를 도구 데이터로 그리고, 글 계획은 표시하지 않는다.
`planGuard` 는 `plan_set` 호출을 "계획 있음"으로 인정한다.

### 3.2 계획 변경 대조

**도구 경로 (정확)**: 직전 `plan_set` 과 비교해 id 로 맞춘다.

| 변화 | 판정 | 표시 |
|------|------|------|
| 새 id | 추가 | `+` 초록 |
| 사라진 id (미완료) | 삭제 | 취소선 + `reason` |
| 같은 id, 제목 다름 | 이름 변경 | `✎` 이전 제목을 툴팁에 |
| 같은 id, 역할 다름 | 역할 변경 | `B → D` |
| 순서만 다름 | 재배치 | 표시 없음, 새 순서로 그림 |

한 턴의 계획 변경은 "계획 변경 n차" 구분선으로 남는다. 구분선은 변경이 일어난 시점(그 `plan_set` 호출 위치)에 들어간다.

**글 계획 경로 (도구가 없을 때만, 추정)**: 지금은 단계 키가 위치(`text:i`)라 다시 쓰면 번호로만 맞는다. 다음 순서로 바꾼다.

1. 역할 표시(`[B]` 등)와 정규화한 제목(공백 · 기호 · 조사 제거, 소문자)이 같으면 같은 단계로 본다.
2. 남은 것끼리 제목 토큰 Jaccard ≥ 0.6 이면 같은 단계로 본다(높은 점수부터 1:1).
3. 완료된 단계가 새 계획에서 안 맞으면 지우지 않고 "완료(계획에서 빠짐)"로 남긴다.
4. 나머지는 추가 · 삭제로 본다.
5. 글 경로로 맞춘 변경에는 "추정" 표시를 붙인다.

### 3.3 역할 판정

| 근거 | 우선순위 | 비고 |
|------|---------|------|
| `plan_set` 의 `role` | 1 (선언) | 칩 "예정" 의 기준 |
| 글 계획의 `[A]`~`[E]` 표시 | 2 (선언) | |
| 실행 기록 | 3 (실제) | 아래 규칙 |
| 위 셋 다 없음 | 4 (추정) | 실행 기록 규칙을 그대로 쓰되 "추정" 표시 |

실행 기록 규칙 (`web/src/lib/roles.ts` 한 곳에 둔다):

- `Agent`(`Task`) 도구의 `subagent_type`: `vibrato-planner` → B, `vibrato-designer` → C, `vibrato-verifier` → E
- 메인의 Edit · Write · NotebookEdit · Codex `FileChange` → D
- 메인의 검증 명령(`npm (run )?(test|typecheck|lint)`, `node --test`, `vitest`, `pytest`, `go test`, `cargo test`, `browser_*` 도구) → E
- 그 밖(읽기, 검색, 질문) → A

선언과 실제가 다르면(선언 B 인데 수정이 일어남) 단계의 역할 표시에 둘 다 보이고, 칩은 실제 역할도 켠다. 경고는 하지 않는다.

### 3.4 하위 에이전트 결과 형식과 인용 대조

B · C 는 마지막 메시지에 JSON 블록 하나를 낸다.

```json
{ "role": "B",
  "items": [ { "claim": "결제 버튼은 약관 동의 전 비활성", "quote": "약관에 동의하기 전에는 결제 버튼을 누를 수 없다", "source": "notion:https://…#결제-조건" } ],
  "missing": [ "환불 버튼 노출 조건이 문서에 없음" ],
  "coverage": [ "결제 조건", "결제 수단", "오류 처리" ] }
```

E 는 다음을 낸다.

```json
{ "role": "E", "verdict": "pass | fail | partial",
  "checks": [ { "what": "버튼 간격", "result": "16px", "evidence": "gap: 16px" } ] }
```

서버 처리 (`server/roleReports.ts`):

1. `PostToolUse` 훅에서 `agent_id` 가 있는 호출의 `tool_response` 텍스트를 에이전트별로 모은다(에이전트당 최대 4MB, 넘으면 오래된 것부터 버림).
2. `SubagentStop` 훅에서 `last_assistant_message` 의 JSON 을 파싱한다.
3. 각 `quote`(E 는 `evidence`)를 정규화(NFC, 공백 압축, 마크다운 `*` `_` `` ` `` 제거)해 모은 원문에 부분 문자열로 있는지 본다. 4글자 미만 인용은 실패다. 숫자는 정규화하지 않는다.
4. 실패 항목이 있고 `stop_hook_active` 가 false 면 `decision: 'block'` 으로 실패 항목만 적어 한 번 돌려보낸다. 두 번째는 통과시키고 그 항목을 "검증 실패"로 표시한다.
5. JSON 파싱이 안 되면 형식만 다시 요구해 한 번 돌려보낸다. 두 번째도 안 되면 `parseError` 로 표시하고 원문 메시지는 그대로 A 에게 간다.
6. 결과를 `role.report` 이벤트(`{ agentId, toolUseId, role, total, verified, failed: [...], missing, coverage, verdict?, parseError? }`)로 보낸다.
7. 같은 내용을 세션 사이드카 파일(`<config>/role-reports/<agentSessionId>.jsonl`)에 남긴다. 기록을 다시 불러올 때 `toolUseId` 로 붙인다. 지금의 `verify` 같은 서버 이벤트는 기록 다시 불러오기에 남지 않기 때문이다.

A 에게 보내는 지시: "인용 확인" 항목은 다시 확인하지 말고 쓴다. "검증 실패" 와 `missing` 만 직접 보거나 사용자에게 묻는다.

하위 에이전트 지시문의 자기 재확인: 결과를 내기 전에 원문 목차(문서 제목들, Figma 프레임 목록)와 `coverage` 를 한 번 대조해 빠진 섹션이 없는지만 본다.

### 3.5 순서 강제 (훅)

- `UserPromptSubmit`: 역할 분담이 켜져 있으면 `PLAN_REMINDER` 에 역할 규칙 한 줄을 더한다.
- `PostToolUse`(메인만): 이번 턴에 파일을 바꿨는지 기록한다.
- `Stop`: 기존 계획 검사에 더해, 파일을 바꾼 턴인데 E 역할 단계도, `plan_step` 의 "Not done: 검증 생략 이유"도 없으면 한 번 돌려보낸다. 파일을 바꾸지 않은 턴은 검사하지 않는다.

### 3.6 계획 탭 UI

**역할 칩 막대**: 턴 카드마다 체크리스트 위. 진행 중인 턴의 막대는 탭 위쪽에 sticky.

- `grid grid-cols-5 gap-2`, 너비를 꽉 채우고 간격만 같게. `rounded-md` 직사각형 버튼 모양. 다섯 개는 항상 그린다.
- 상태: 미사용(흐림, 비활성) · 예정 · 진행 중 · 답변 대기 · 사용자 응답 대기 · 완료 · 실패 · 중단.
- 칩 아래 줄: 단계 수(완료/전체), 재시도 회차가 있으면 `×2`.
- 누르면 그 역할의 첫 단계로 스크롤하고 그 역할 단계를 강조한다. 다시 누르면 해제.
- 역할 분담이 꺼진 세션에서는 막대를 그리지 않는다.

**단계 행**: 앞에 역할 태그(`B`). 추정이면 점선 테두리.

**단계 안의 주고받기 줄**:

```
2. [C] 시안 수치 확인                                   진행 중
   → C 에게 요청: 결제 화면 노드 12:34 배치 · 문구         0:42 대기
   ← C 답변: 항목 9개 · 인용 확인 8 · 실패 1 · 빠짐 1
   ↳ A 처리: 실패 1건(버튼 문구)은 사용자에게 질문
   ⏸ 사용자 응답 대기: "버튼 문구가 시안과 기획서에서 다릅니다…"
```

- 요청 줄: `TaskInfo.description` + 원본 위치. 대기 시간은 실시간.
- 답변 줄: `role.report` 집계. 누르면 실패 · 빠짐 항목 목록이 펼쳐진다.
- 처리 줄: 그 단계의 `plan_step` 메모.
- 대기 줄: 그 단계 동안 생긴 `pending`(질문 · 승인).

**계획 변경 · 추가 요청**:

- `PlanTurn.additions` 를 `{ text, itemId, at }[]` 로 바꿔, 추가 요청이 들어온 위치에 "추가 요청" 줄을 끼운다.
- 그 뒤 `plan_set` 이 다시 불리면 "계획 변경 n차" 구분선과 §3.2 의 변화 표시가 붙는다.

**예외 상황**:

| 상황 | 단계 | 칩 |
|------|------|-----|
| 하위 에이전트 오류 · 시간 초과 (`TaskInfo.error`) | 빨간색, 원인 표시 | 실패 |
| 권한 거부 | 거부 표시 | 해당 역할 실패 |
| 사용자 중단 | 진행 중 단계 "중단" | 진행 중 역할 → 중단 |
| E 실패 → D 수정 → E 재검증 | 같은 단계 b · c 회차 | E `×2` |
| 인용 검증 실패 | 답변 줄에 실패 수 | 완료(경고색 숫자) |
| 보고 형식 오류 | 답변 줄 "형식 오류" | 완료(경고색) |
| 세션 재개(resume) · 기록 다시 불러오기 | 도구 호출과 사이드카로 다시 그린다 | 같은 상태 |

**탭 전체 보기**: `SessionSummary` 를 넓혀 턴마다 쓴 역할, 걸린 시간, 실패 · 재시도 수를 한 줄로 보인다.

### 3.7 설정 · Codex

- `config.ts` 에 `roleMode?: boolean`. `/api/settings/role-mode` GET/POST. 도구 패널에 "역할 분담" 체크박스(문구는 i18n en/ko), "항상 계획 세우기"가 꺼지면 비활성.
- 새 세션부터 적용한다. 켜면 Claude 세션에 `agents` 세 개, 역할 지시문, 훅 확장이 붙는다.
- Codex: 역할 지시문 중 "하위 에이전트" 부분을 빼고 넣는다. B · C · E 단계도 A 가 직접 한다. `plan_set` 의 역할은 그대로 받아 칩이 켜진다.

### 3.8 A(총괄) 지시문 요지

`server/planInstructions.ts` 에 역할 분담이 켜졌을 때만 붙는 `ROLE_INSTRUCTIONS` 로 둔다.

1. 일반 질문 · 즉답 요청이면 역할을 나누지 않고 바로 답한다(계획 프로토콜은 그대로).
2. 코드를 바꾸는 요청이면 `plan_set` 으로 단계마다 역할을 정한다. 필요 없는 역할은 넣지 않는다.
3. 기획 · 디자인 자료는 이 순서로 찾는다: 이번 메시지의 첨부 · 링크 → 이 세션에서 이미 받은 B · C 답변 → 이 세션에 붙은 자료 → 없으면 사용자에게 한 번에 요청.
4. 자료가 짧으면(붙여 넣은 몇 줄, 캡처 한 장) B · C 를 부르지 않고 직접 읽는다.
5. B · C · E 에게는 원본 위치와 확인할 범위만 넘기고, 자료를 풀어 쓰지 않는다.
6. "인용 확인" 항목은 다시 확인하지 않는다. "검증 실패" 와 `missing` 만 처리하고, 질문은 모아서 한 번에 묻는다.
7. 수정한 턴은 E 단계로 끝내거나, 생략하면 `plan_step` 에 이유를 적는다. 타입 검사 한 줄로 끝나는 확인은 E 를 부르지 않고 직접 한다.
8. 계획을 바꾸면 `plan_set` 을 다시 부른다. 완료된 단계는 남기고 `reason` 을 적는다.

### 3.9 하위 에이전트 토큰 절약

| # | 방법 | 적용 | 줄어드는 것 |
|---|------|------|------------|
| T1 | `omitClaudeMd: true` | B · C · E 정의. E 에 필요한 실행 명령(테스트 · 개발 서버)은 A 가 요청에 적어 넘긴다 | 호출마다 CLAUDE.md(지금 사용자 전역 + 프로젝트 합쳐 14KB) |
| T2 | 역할별 도구 · MCP 제한 | `tools` 허용 목록 또는 `mcpServers`. B 는 Notion 류, C 는 Figma 류, E 는 vibrato 브라우저 + Bash. Agent · Skill · Task 류 도구는 모두 뺀다 | 도구 정의 토큰, 엉뚱한 도구 탐색 |
| T3 | 시스템 프롬프트 고정 | 역할 지시문에 날짜 · 경로 · 세션 값을 넣지 않는다. 바뀌는 내용은 전부 요청 메시지로 보낸다 | 두 번째 호출부터 시스템 프롬프트가 캐시로 읽힌다 |
| T4 | 작게 먼저 읽기 | C: `get_metadata` 로 구조만 본 뒤 필요한 노드만 `get_design_context`. B: 페이지 전체 대신 해당 블록. E: 출력은 `tail` · `grep` 으로 자른다 | 큰 원문 입력 |
| T5 | 이미지 대신 수치 | E 는 `browser_measure` · `browser_snapshot`(root 지정)을 먼저 쓰고, 스크린샷은 수치로 판단할 수 없을 때만 찍는다 | 이미지 입력 토큰 |
| T6 | 결과 재사용 | 같은 세션 안에서는 이전 답변이 대화에 있으니 다시 부르지 않는다(§3.8-3). 세션을 넘어서는 원본 위치를 키로 사이드카에 캐시하고, 답변 줄에 "캐시 · n시간 전"을 표시한다. 사용자가 새로 읽기를 고를 수 있다 | 같은 문서를 다시 읽는 비용 |
| T7 | 이어 묻기 | 같은 문서에 대한 추가 질문은 새 B 를 띄우지 않고 `SendMessage` 로 끝난 B 에게 묻는다. B 는 이미 읽은 원문을 맥락에 가지고 있다 | 원문 재수집 |
| T8 | 상한 | `maxTurns`(B · C 15, E 25), `effort` low~medium, `autoCompactWindow` 를 낮게 | 헤매는 탐색 |
| T9 | 출력 형식 고정 | §3.4 의 JSON 만 내게 한다. `claim` 은 한 줄, 설명 문장 금지 | 하위 에이전트 출력과, 그 출력이 들어가는 메인 컨텍스트 |

- T1 · T2 · T3 은 P3 · P4 에서 정의와 함께 넣는다. T6 의 세션 간 캐시와 T7 은 P6 에서 측정을 보고 넣는다.
- T6 캐시는 원본이 바뀌어도 서버가 알 수 없다(사용자의 Notion · Figma 인증은 CLI 에만 있다). 그래서 기한(기본 24시간)과 수동 새로 읽기로 다룬다.

## 6. 효과 판단과 중단 기준

역할 분담이 코드 품질을 올리는 경로는 세 가지뿐이다. 나머지는 사용자가 보기 편해지는 것이다.

| 요소 | 정확도에 주는 효과 | 근거 |
|------|------------------|------|
| E 와 `Stop` 검증 강제 | 큼 | 검증을 빠뜨린 수정이 없어지고, 긴 실행 로그가 메인 컨텍스트에 쌓이지 않는다 |
| B · C 인용 대조 | 중간 | 원문에 없는 값을 지어내는 오류를 막는다. 해석 오류는 못 막는다 |
| B · C 의 원문 요약 | 중간(자료가 클 때만) | 큰 Notion · Figma 원문이 메인 컨텍스트를 채우지 않아 메인의 판단이 흐려지지 않는다. 자료가 작으면 효과 없음 |
| `plan_set` | 없음(코드), 큼(체크리스트) | 계획 탭의 정확도 문제를 푼다 |
| 역할 칩 · 주고받기 UI | 없음(코드) | 사용자가 진행을 보고 일찍 끼어들 수 있게 한다 |
| 역할을 나눈다는 사실 자체 | 없음 | 모델이 더 똑똑해지지 않는다. 작은 작업에는 오히려 부담 |

중단 기준 (P6 에서 판단):

- TC-QA 에서 QA-1 · QA-2 가 꺼짐보다 나아지지 않으면 B · C 를 끄고, `plan_set` · E · 검증 강제 · UI 만 남긴다.
- TC-CO 의 CO-1 을 넘고 QA 도 나아지지 않으면 역할 분담 토글을 기본 꺼짐으로 두고 더 개발하지 않는다.

## 7. 남은 위험

- 원문 해석 오류: 어떤 구조에서도 생긴다. E 검증과 사용자 확인이 안전장치다.
- 빠진 항목: 인용 대조로는 못 잡는다. `coverage` 와 자기 재확인 한 번, A 의 `missing` 질문으로 줄인다.
- 글 계획 경로의 대조 · 역할 추정은 틀릴 수 있다. "추정" 표시로 구분하고, 역할 분담을 켠 세션은 `plan_set` 을 쓰게 한다.
- SDK 훅 입력(`agent_id`, `last_assistant_message`)이 바뀌면 인용 대조가 멈춘다. `tests/role-reports.test.ts` 가 훅 입력 모양을 고정해 둔다.
